# Как я пытался определить возраст Telegram-аккаунта по ID

[English](README.md)

Мне нужна была дата, желательно с точностью до дня. Сервисы проверки возраста Telegram-аккаунтов уже выдавали даты, иногда даже с часами и минутами, так что я решил выяснить, откуда они берут эти числа. Может, есть таблица, скрытое поле или серверный метод. Что-то, что можно проверить и перенести в небольшой офлайн-скрипт.

Скрипт остался небольшим. Исследование разрослось.

Я проследил, как собирались открытые датасеты, изучил схему Telegram, проверил метаданные аккаунтов и старые фотографии профиля, разобрал Android-клиенты, сравнил методы интерполяции и опросил ботов, которые определяют дату регистрации. Несколько обнадёживающих находок рассыпались, когда я проверил, к какому событию на самом деле относятся временные метки. Сам тоже ошибался: смешивал ID каналов и пользователей, оценивал модель после очистки её тестовых данных, связал две независимые настройки ботов только потому, что их имена встретились в одном Java-файле.

В этом репозитории лежит получившийся оценщик, [main.py](main.py), а ниже я по порядку описал исследование. Скрипт **не восстанавливает** точную дату регистрации для любого Telegram ID. Встроенные в него числа зафиксированы по результатам подгонки модели на исследовательских данных, в том числе на источниках с не до конца проверенным происхождением. По ним можно получить приблизительную дату, но нельзя доказать, когда человек завёл аккаунт.

<a id="run-the-script"></a>

## Обновление алгоритма

Интерфейс скрипта прежний: запускаешь `python3 main.py`, вводишь ID, получаешь дату с погрешностью. Можно передать ID аргументом при запуске. Пакеты, сеть и дополнительные файлы данных не нужны.

В общих таблицах учтены три присланные даты: 8874594977: 17.06.2026, 3941874: 31.12.2013, 5869015726: 21.01.2023. При обучении их вес равен 10, остальных записей 1. Они влияют на общую кривую, а не на отдельный справочник ответов. Четыре ошибочных источника исключены. Присланные даты независимо по данным Telegram не подтверждены.

На повторных отложенных проверках 223 разных ID (816 зависимых предсказаний) медианная ошибка составила 42.58 дня, p80 89.14 дня, средняя ошибка 53.82 дня. Относительно исходной версии p80 немного улучшился, медиана и средняя ошибка ухудшились. Это не доказывает общего прироста точности и не гарантирует интервал для любого аккаунта.

Дополнительно скачаны 46 публичных файлов с закреплёнными версиями и разобраны 17 таблиц или наборов констант. Новых независимо подтверждённых дат не найдено. Дубли и константы чужих оценщиков не считались новыми наблюдениями.

## Как запустить скрипт

Нужен Python 3. Устанавливать пакеты не придётся, сетевых запросов скрипт не делает.

```sh
git clone https://github.com/sepiol026-wq/telegram-id-age-research.git
cd telegram-id-age-research
python3 main.py 103151531 5000000000
```

Пример вывода:

```text
103151531 2015-05-30 16:13:09 UTC +- 91 d  [ 2015-02-28 .. 2015-08-29 ]
5000000000 2021-11-30 12:15:35 UTC +- 91 d  [ 2021-08-31 .. 2022-03-01 ]
```

Дата и интервал приблизительные, не официальные сведения о регистрации. Время суток вычислено интерполяцией, а не измерено.

## Месяц, который Telegram уже отдаёт

Для первого полезного результата оценщик вообще не понадобился. В `peerSettings` у Telegram есть поле `registration_month`. В [документации панели действий](https://core.telegram.org/api/action-bar) описаны сведения о регистрации, которые показываются, когда кто-то впервые вам пишет. В том же конструкторе есть поля со страной телефонного номера и недавними изменениями имени или фотографии.

Различать их нужно потому, что эти значения относятся к разным событиям:

```text
registration_month  -> a month such as 08.2017
name_change_date    -> a timestamp for a name change
photo_change_date   -> a timestamp for a photo change
```

Я получил значения месяца через `messages.getPeerSettings`. Для других пользователей возвращался объект настроек без этого поля. Отсутствие необязательного поля не было ошибкой парсера. Telegram просто не передал его в этом ответе.

Проверка на двух аккаунтах показала, что направление имеет значение: после сообщения с одного аккаунта на другой получатель видел месяц регистрации отправителя. Обратный запрос тех же сведений не давал. Позднее обходы участников групп оказались гораздо менее результативными, чем просмотр уже существующих личных переписок.

Для отдельного аккаунта это был полезный источник, но задача с инструментом оставалась нерешённой. Офлайн-функция, на вход которой приходит только целое число, не может запросить у Telegram `peerSettings`. Даже онлайн-версии нужно получить peer, обычно вместе с access hash. С этим может помочь публичный юзернейм или сущность, уже известная сессии. Само по себе число не открывает доступ к объекту любого пользователя.

Сначала я описывал это как ограничение по наличию в контактах. Формулировка оказалась слишком гладкой. Добавление человека в контакты не гарантировало появления месяца, а описанный в документации интерфейс первого обращения устроен сложнее, чем проверка записи в адресной книге. По результатам я могу утверждать только, что доступность зависит от отношений между аккаунтами и ответа сервера. Полного правила, по которому можно заранее предсказать наличие поля, я не восстановил.

<a id="the-first-interpolation-table"></a>

## Первая таблица для интерполяции

Для офлайн-версии я взял обычную интерполяцию: собрать пары ID пользователя и даты, отсортировать по ID, найти две соседние опорные точки и оценить временную метку между ними.

```text
t = t0 + (t1 - t0) * (id - id0) / (id1 - id0)
```

Если бы ID выдавались настоящим хронологическим счётчиком с относительно стабильным темпом, это могло бы хорошо работать. Общая связь между величиной Telegram ID и возрастом к такому решению подталкивала: старый маленький ID и недавний большой ID обычно относятся к разным периодам.

Но в локальных данных даты не всегда росли вместе с ID. У большего ID могла быть более ранняя указанная дата. Часть случаев могла объясняться особенностями выделения номеров. Часть, неверными метками. А где-то сайт проверки возраста мог просто публиковать ответ другого сайта проверки возраста. Пока эти случаи не разобраны, кривая через все точки лишь превращала бы противоречивые метки в резкие скачки.

Я применил изотоническую регрессию, конкретно PAVA, чтобы получить неубывающую последовательность оценок. Если значения в соседних блоках нарушают порядок, PAVA объединяет блоки и заменяет их значения взвешенным средним. Так продолжается, пока даты в подогнанной последовательности не перестают убывать.

Это допущение модели. Оно не доказывает, что Telegram выдаёт ID в монотонном порядке. И каждая отдельная известная дата при этом не сохраняется. Если дата одного аккаунта выбивается из порядка соседних точек, PAVA может заметно сдвинуть её при подгонке. Позже это случилось даже с месяцем, который сообщил сам Telegram.

В ранней версии было 84 опорные точки после подгонки. Потом объём входных данных вырос примерно до 238, затем до 249 записей. Точные количества менялись, потому что источники пересекались, а некоторые записи я заменял. В итоговом зафиксированном генераторе 491 уникальный положительный ID; в самом скрипте хранится меньший набор узлов подогнанной кривой.

Программа уже печатала временную метку. Оснований для секунд в ней у меня ещё не было.

<a id="a-timestamp-belonging-to-the-wrong-event"></a>

## Временная метка не того события

`account.getAuthorizations` возвращает `date_created` и `date_active` для авторизаций. Это точные временные метки, а в исследовании дат создания очень легко приписать имени `date_created` больше смысла, чем оно несёт.

Авторизация относится к сеансу входа. Время её создания не становится автоматически временем создания аккаунта.

В ранних заметках я считал самую старую доступную авторизацию временем регистрации для аккаунтов, которые выглядели свежими. Для такого вывода нужны независимые доказательства, что авторизация появилась именно во время регистрации. У старого аккаунта после недавнего входа может остаться только новая сессия. Отозванные сессии не сохраняются в виде доступного полного журнала всей истории.

Ещё я неверно истолковал TTL авторизации как максимальный возраст сессии. Срок истечения из-за неактивности не означает, что любая сессия исчезает через фиксированное число дней после создания. Сессию можно поддерживать активной, а можно оставить без использования. Это разные случаи.

Особенно сбили с толку пять ID с временными метками авторизаций, уложившимися в 243 секунды. Разница между крайними ID составляла примерно 267 миллионов. В поздних пересказах эти пять случаев превратились в контролируемое создание ботов через BotFather. Однако ранние записи показывают: метки были взяты из авторизаций импортированных аккаунтов. Это разные эксперименты. Пять записей остались в историческом наборе калибровочных данных. В том числе поэтому я не называю его чистым датасетом достоверных дат регистрации.

Отдельные наблюдения за BotFather в рабочем журнале действительно показали, что ID только что созданных ботов шли не по числовому порядку. Эти наблюдения противоречат модели простого возрастающего счётчика. Но они не раскрывают весь механизм выделения ID, не доказывают равномерную случайность и не задают универсальный математический предел точности.

В то время я записал гораздо более сильные выводы. Если различать регистрацию и вход в аккаунт, они не выдерживают проверки.

<a id="borrowing-the-wrong-id-sequence"></a>

## Чужая последовательность ID

Следующей зацепкой стало исследование ID каналов от [TGScope](https://tgscope.io/rnd/telegram-channel-id-clock). В рабочем журнале я записал его разбор 247,850 каналов с известными датами и интерпретацию через сменяющиеся диапазоны выдачи ID.

Отсюда возникла идея другого оценщика: определить период, в котором использовался диапазон, и возвращать этот период. Не выдавать положение внутри диапазона за точные часы.

Ошибка была в переносе границ каналов на пользователей. И там и там целые числа, но Telegram различает [пространства ID сущностей](https://core.telegram.org/api/bots/ids). Измерения для новых каналов и современных им пользователей не укладывались в общую шкалу. Канал с ID около миллиарда мог быть на годы старше пользователя с близким числовым ID.

Предполагаемую границу смены режима я пересматривал несколько раз. Сначала взял её из исследования каналов. Затем передвинул в диапазон пользователей, не собрав достаточных доказательств. Позже подсчёт инверсий указал на общее различие по разные стороны слабо заполненного промежутка между старыми ID около 2.3 миллиарда и новыми данными выше 5 миллиардов. Ни один из этих пересмотров не означает, что я восстановил реальный алгоритм выдачи ID в Telegram.

Из эксперимента с каналами всё же вышло полезное правило: не смешивать типы объектов в обучающей выборке. Даты каналов, месяцы регистрации пользователей и временные метки авторизаций не становятся взаимозаменяемыми наблюдениями только потому, что их можно записать парами `(integer, timestamp)`.

Я также проверял `channel.date`. Значение этого поля и то, какой именно объект вернулся, нужно разбирать с учётом вызванного метода API и статуса участия в канале. Кешированные сущности усложняли эти проверки. Даты каналов я не оставил в качестве опорных дат регистрации пользователей, и режима определения возраста каналов в этом репозитории нет.

<a id="finding-the-signup-notices"></a>

## Уведомления о регистрации

Сборщик из [Jobians/telegram-id-age](https://github.com/Jobians/telegram-id-age) дал больше, чем ещё одна таблица чисел. Его `src/updateDataset.js` ищет в диалоге служебное сообщение с `messageActionContactSignUp` и берёт дату этого сообщения.

Здесь уже можно проследить, откуда взялось событие. [Конструктор Telegram](https://core.telegram.org/constructor/messageActionContactSignUp) обозначает регистрацию контакта. Для метки с точностью до дня это куда более подходящий кандидат, чем дата, угаданная по соседнему ID.

Но нужны две отдельные проверки. Во-первых, сборщик должен связать служебное сообщение с правильным пользователем. Во-вторых, чтобы считать каждую запись открытого датасета независимо проверенной, нужно знать происхождение каждой строки. Прочитав сборщик, я понимаю, как он может получать данные. Это не доказывает, что все строки в репозитории получены именно им и потом не редактировались.

В исследовательских заметках записан небольшой локальный сбор событий регистрации. Позже гораздо более масштабный обход с другого аккаунта не нашёл ни одного. Противоречия тут нет: разные истории контактов могут давать доступ к разным сообщениям. Проблема была в моей привычке объявлять любой успешный сбор полным, а после неудачного считать сбор невозможным. У позднего обхода была ошибка пагинации, о ней ниже.

Открытый датасет из 212 записей стал одним из основных источников. После дополнений в моей рабочей копии было 214 строк. Эти числа относятся к разным файлам, а не показывают рост исходного репозитория.

<a id="teaching-the-estimator-to-show-uncertainty"></a>

## Как я добавил оценку неопределённости

Одну временную метку слишком легко принять за установленный факт. Я добавил интервал, рассчитанный по ошибкам предсказаний в окрестности соседних ID.

Сначала использовал проверку с исключением по одной точке, leave-one-out: убирал точку, подгонял модель по остальным, предсказывал исключённую и записывал ошибку. Позже перешёл к повторным разбиениям на обучающую и отложенную выборки. Генератор перемешивает входные данные, обучается на 70 процентах и измеряет абсолютные ошибки на оставшихся 30 процентах. Он повторяет это для 12 значений seed.

Здесь я поймал простую ошибку в реализации. PAVA требует, чтобы данные были упорядочены по ID. Одна версия подгоняла модель по перемешанной обучающей части без предварительной сортировки, из-за чего получались абсурдные ошибки. Сортировка внутри функции подгонки исправила этот баг. Качество самих дат она не исправила.

Для таблицы неопределённости берутся локальные наборы ошибок на отложенных данных. Код выбирает окно по индексам: по 12 позиций с каждой стороны от опорной точки и саму её позицию. Получается до 25 записей, хотя в старом описании было «24 ближайшие опорные точки». У краёв записей меньше. Соседство по индексам к тому же не обязательно означает наименьшее числовое расстояние между ID.

Для каждого окна генератор выбирает значение примерно на уровне 80-го процентиля и сохраняет его в целых днях. При запуске скрипт интерполирует эту таблицу вместе с таблицей дат.

Так был построен интервал. Обещания, что в него попадут 80 процентов будущих Telegram-аккаунтов, из этого не следует. Родственные датасеты могут переносить одни и те же исходные сведения через границу случайного разбиения. Ошибки различаются по эпохам. Сами метки тоже могут быть оценками. В рабочем журнале я написал «80 процентов аккаунтов попадают внутрь», но такой вывод обо всей совокупности аккаунтов эксперимент не подтверждал.

<a id="the-profile-photo-detour"></a>

## Попытка использовать фотографии профиля

Фотографии профиля выглядели многообещающе: Telegram отдаёт их даты с точностью до секунды. Если человек загружает первый аватар при регистрации и сохраняет его, самая старая видимая фотография может быть близка по времени к регистрации.

Крошечная ранняя выборка обнадёживала. В заметках четыре из пяти сравнений укладывались в сутки, а в одном фотография была заметно позднее. Я превратил это в утверждения о работающем методе с точностью до дня для свежих аккаунтов. Поспешил. У меня не было способа установить, что самая старая сохранившаяся фотография произвольного аккаунта действительно была его первой фотографией.

Люди удаляют старые аватары. Кто-то годами оставляет аккаунт без фотографии. Если сейчас у аккаунта одна фотография, это не доказывает, что у него никогда не было других.

Использовать можно верхнюю границу даты регистрации:

```text
account registration <= a photo upload belonging to that account
```

Это не равенство. Даже точность временной метки до секунды не устанавливает недостающую связь между событиями.

Я всё равно попробовал добавить даты фотографий в обучающую выборку. Ранний небольшой эксперимент ухудшил кривую. В более позднем наборе было 1,867 наблюдений по фотографиям. Когда я использовал их даты как точки регистрации, записанная медианная ошибка на отложенных данных выросла примерно до 355 дней. У существовавшей модели на смешанных источниках она была около 34 дней. Старые ID с недавно загруженными фотографиями сдвигали большие участки монотонной кривой к недавним датам.

Я убрал эти наблюдения из данных для точечной подгонки. В локальном эксперименте с онлайн-уточнением фотографию всё ещё можно было использовать как верхнюю границу для того же аккаунта. Превратить эту границу в точный день рождения нельзя. Безопасно переносить ограничение от фотографии одного ID на другие ID тоже нельзя, если одновременно наблюдаются инверсии в предполагаемом хронологическом порядке.

Опубликованный скрипт фотографии не запрашивает. Я оставил эту часть истории, потому что это была одна из самых заманчивых ошибочных идей за всё исследование.

<a id="opening-the-android-clients"></a>

## Что нашлось в Android-клиентах

Один форк Telegram показывал оценку даты создания аккаунта со временем суток. Я захотел проверить, не использует ли клиент какой-то API, который я упустил.

В изученном коде exteraless экран профиля вызывал `ProfileDateHelper.getUserTime`. Этот класс загружал ресурс `id_date.json`, находил соседние ID и выполнял линейную интерполяцию. В интерфейсе стоял знак приблизительного значения. В зафиксированном ресурсе было 144 опорные точки.

Минуты на экране появлялись при форматировании интерполированной временной метки. Отдельного измерения, которое давало бы основания для этих минут, не было.

В APK AyuGram нашлась ещё одна реализация в `com.exteragram.messenger.regdate`. На декомпиляцию всего APK не хватило памяти, поэтому я изучил нужные DEX-файлы отдельно. Из `RegDateController` вышел на ресурс `extera/registration_dates.bin`.

Файл был закодирован невидимыми символами Unicode. `InvisibleEncryptor` восстанавливал байты с помощью алфавита из одиннадцати символов и разделителей. Сложность была в узком неразрывном пробеле `U+202F`: в выводе декомпилятора его легко принять за обычный пробел. Декодирование заработало, когда я стал смотреть на кодовые точки, а не доверять тому, как символы отображаются.

Получилось 150 пар ID и даты. Новый файл мало пересекался с таблицами из ранее изученных форков, поэтому заметно изменил подгонку. Данные я действительно нашёл новые, но это всё ещё были опорные значения, встроенные в чужой оценщик. Само по себе нахождение в бинарном файле внутри APK не делает их достовернее.

Локальный запасной путь в `RegDateController` сочетал интерполяцию с датой самой старой доступной фотографии профиля. У клиента был и отдельный путь удалённого запроса, а также тип ответа с флагами вроде `EXACT`, `INTERPOLATED`, `LT` и `ET`.

Эти флаги описывают категории, с которыми умеет работать клиент. Они не объясняют, как сервер устанавливает достоверную дату, какая часть его базы содержит точные значения и поможет ли подписка этому проекту. Доступный разработчикам метод `addregdate` подтверждал поддержку записей, добавленных вручную. Он не доказывал ни того, что все удалённые записи внесены вручную, ни того, что сервер использует только встроенные 150 точек.

<a id="more-anchors-and-a-better-looking-mistake"></a>

## Новые опорные точки и красивая ошибка

Объединение данных из форков с прежней коллекцией улучшило часть записанных показателей ошибки. В рабочем журнале была версия на 353 точках, затем примерно на 490 после декодирования ресурса и, наконец, на 491 после принятия ещё одной записи-кандидата.

Прирост был скромнее, чем можно было ожидать по числу просмотренных репозиториев. Несколько проектов повторяли одну и ту же таблицу. При сравнении копия WizardLoop совпала с данными Jobians. В других источниках встречались подозрительно круглые ID или даты, которые не согласовывались с соседними метками. Дубликат не даёт независимого подтверждения.

Я попробовал удалять выбросы. Первый результат выглядел отлично: верхний процентиль ошибки уменьшился почти вдвое. Потом я проверил порядок оценки. Я очистил весь датасет ещё до того, как разделил его на обучающую и тестовую части. Будущие тестовые метки уже повлияли на то, какие точки остались.

Когда я повторил удаление выбросов отдельно внутри каждой обучающей части, большая часть улучшения пропала. Остаточные изменения зависели от порога и были достаточно малы, чтобы я не стал сохранять дополнительную обработку.

В других экспериментах я представлял месячные наблюдения интервалами, снижал веса подозрительных дат, сдвигал месячные метки к середине месяца и повышал вес месяцев, полученных от сервера. Ни один вариант не дал устойчивого улучшения, ради которого стоило бы заменять простую подгонку. В заметках есть и попытки со сплайнами и методами на основе плотности, тоже без убедительного выигрыша. Публиковать неподтверждённый рейтинг по этим пробным запускам я не стал.

Даже увеличение веса месячной метки не заставляло кривую точно её соблюдать. PAVA балансирует соседние наблюдения. Если я знаю от Telegram месяц регистрации конкретного аккаунта, для этого аккаунта нужно прямо использовать известный факт, а не надеяться, что сглаженная кривая сама его воспроизведёт.

<a id="the-month-field-did-not-scale"></a>

## Массовый сбор месяца регистрации не сработал

Я вернулся к `registration_month`: это всё ещё был прямой ответ сервера, а не очередная таблица для интерполяции.

Ранние проверки личных диалогов дали несколько полезных значений. Более крупные обходы участников групп в основном ничего не давали. В рабочем журнале для широкого обхода записаны 2,954 кандидата и три найденных месяца. Все три случая были связаны с личными диалогами. Эта выборка не измеряет долю всех пользователей Telegram, чей месяц можно увидеть. Она описывает конкретные сессии и конкретных собеседников.

Скрипт онлайн-уточнения всё же мог улучшить отдельный результат. В одном записанном случае серверный месяц оказался целиком за пределами интервала, предсказанного офлайн-кривой. Механическое пересечение дало бы пустой ответ. Правильнее было отметить расхождение и для этого аккаунта предпочесть месяц, который напрямую сообщил сервер.

Заодно получился конкретный контрпример к представлению об интервале модели как о жёсткой границе. Добавление достоверного наблюдения в обучающую выборку не гарантирует, что подгонка с регуляризацией его воспроизведёт.

Соседние поля задачу определения дня не решили. `name_change_date` отмечает время изменения имени. Чтобы вывести из него регистрацию, нужно знать, что пользователь никогда не менял имя и что начальное заполнение поля по смыслу совпадает с регистрацией. Ни того ни другого я не установил. С `photo_change_date` та же проблема.

<a id="trying-to-separate-the-data-centers"></a>

## Попытка разделить дата-центры

Возможно, видимый беспорядок возникал из-за смешивания нескольких потоков выдачи ID. Если каждый дата-центр выделял ID по-своему, разделение датасета могло показать более ясную зависимость.

Я собрал набор из 690 наблюдений с информацией о дата-центрах, полученной из данных фотографий. Предварительные сравнения не показали более аккуратной хронологической последовательности внутри одного DC. Но проверка всё ещё использовала даты фотографий как замену датам регистрации. Задержка между ними была достаточно большой, чтобы скрыть возможный эффект механизма выдачи ID.

Было и другое несоответствие: DC хранения фотографии не обязательно совпадает с исходным DC регистрации аккаунта. Поле, которое я мог получить, могло оказаться вовсе не тем полем, которое требовалось для проверки гипотезы.

Гипотеза осталась неподтверждённой. Для полезного эксперимента нужно сопоставить надёжно наблюдавшееся событие регистрации с относящимися к аккаунту метаданными DC на тот момент. Разделение шумного набора фотографий на несколько меньших шумных наборов такой проверкой не было.

<a id="rechecking-the-source-of-the-dates"></a>

## Повторная проверка происхождения дат

Исследование всё время возвращалось к одному вопросу: какие записи получены из наблюдений, а какие представляют собой ответы чужой модели?

В нескольких монотонных ресурсах инверсий дат не было вообще. В датасете, ориентированном на события регистрации, они встречались, в том числе в старых периодах. Сначала я считал идеальную монотонность доказательством синтетического происхождения ресурса. Это повод проверить происхождение, но само по себе не доказательство. Отобранный или отфильтрованный набор тоже может оказаться монотонным.

Обратное рассуждение было ничуть не надёжнее. Наличие инверсий не делает датасет автоматически подлинным. Неверные даты тоже создают инверсии.

В прежних запусках leave-one-out я разделял старые и новые диапазоны. В рабочем журнале записаны медианные ошибки около 13 дней для старой части и около 44 дней для новой. Это был не тот же эксперимент, что итоговая многократная проверка на отложенных данных из смешанных источников, а точные определения подвыборок по ходу работы менялись. Представлять эти числа как одну подтверждённую гарантию точности нельзя.

В старой части тоже были нарушения порядка, особенно около 2015 года. Утверждение, что все ID до 2021 года строго хронологичны, было неверным. Более точные опорные точки могут помочь, но одна достоверная старая точка не определяет скорость выдачи между всеми остальными ID.

Я изучил историю датасета Jobians, поискал форки и дополнительные записи, проверил ещё один небольшой репозиторий дат создания. Дополнительные старые точки не дали ожидаемого скачка к точности до дня. Более сложный интерполятор не восстановит информацию, которую не подтверждают входные метки.

В раннем расчёте темпа выдачи была ещё и ошибка единиц: я разделил разницу ID на число секунд в сутках, а не на число прошедших дней. После исправления арифметики число сильно изменилось. Постоянной величиной темп от этого не стал. Поздние попытки вывести окно равномерного распределения ID из попарных разностей опирались на допущения, которые наблюдения не подтверждали. Заявленный в рабочем журнале «физический предел» я не сохранил в качестве результата.

<a id="the-signup-scan-that-returned-nothing"></a>

## Обход истории, который ничего не нашёл

Более поздний сборщик прошёл 2,000 диалогов и не сообщил ни об одной новой опорной точке `messageActionContactSignUp`. Казалось, это направление исчерпано, пока я не проверил, как он перескакивал к старой истории.

ID старого сообщения он оценивал по формуле:

```text
top_message - count + 1
```

ID сообщений не образуют плотный массив индексов внутри каждого диалога. Удаления, пропуски и нумерация между переписками ломают такой расчёт. Этот короткий путь не доказывал, что сборщик дошёл до самых старых сообщений. В более ранней попытке с очень большим `offset_id` я тоже неправильно понял, с какого конца API вернёт историю.

Другой баг был в том, что код смотрел только на массив `chats` из `messages.getDialogs` и пропускал пользователей в отдельном массиве `users`. Из-за этого набор кандидатов оказывался пустым ещё до начала обхода истории.

Обоснованный результат звучит так: этот обход не нашёл опорных точек. Он не доказывает, что у аккаунта их не было, и ничего не говорит обо всех остальных аккаунтах. Для утверждения о полноте пришлось бы идти по реальным результатам пагинации до конца, учитывая ошибки и недоступную историю.

Я не стал повторно собирать данные с частных аккаунтов только ради публикации этого README. В репозитории лежат офлайн-скрипт и результаты исследования, а не файлы сессий или сборщик, который сразу начинает обращаться к Telegram.

<a id="commercial-answers-and-a-broken-comparison"></a>

## Коммерческие ответы и неверное сравнение

Следующим очевидным объектом сравнения были боты, определяющие дату регистрации. Некоторые бесплатно выдавали месяц и рекламировали платные методы API. Я запросил выборку аккаунтов, даты которых уже были в исследовательском датасете.

В сохранённом файле результатов DateReg 20 строк. При проверке перед публикацией я обнаружил, что у одной строки ID равен `0`. Это служебный маркер датасета, а не реальный аккаунт. Именно он давал ранее заявленную максимальную ошибку 625 дней. Использовать этот максимум как свидетельство точности дат аккаунтов было нельзя с самого начала.

Строк с положительными ID было 19. Ни в одном ответе не было проверяемых в этой выборке меток `exact` или `100%`. В четырёх ответах эталонный день попадал в возвращённый календарный месяц.

Первоначально я преобразовал каждый месячный ответ в первый день месяца. Но это измеряет расстояние до произвольно выбранного дня-представителя, а не обязательно ошибку сервиса. Например, ответ «январь» для эталонного 22 января верен с точностью до месяца, хотя от 1 января до этой даты 21 день.

Я пересчитал по сохранённому файлу обе величины:

| Оценка 19 строк с положительными ID | Медианная абсолютная ошибка | Максимум |
| --- | ---: | ---: |
| Считать ответ первым днём указанного месяца | 47 дней | 183 дня |
| Расстояние от эталонного дня до интервала указанного месяца | 19 дней | 153 дня |

Во второй строке ответ, содержащий эталонную дату, даёт нулевую ошибку с точностью до месяца. Сам день он по-прежнему не определяет. Выборка мала, у её меток уже описанные ограничения происхождения, а при опросе бота я не установил строгий протокол сопоставления запросов и ответов по ID сообщений. Это описание сохранившихся ответов, не общий бенчмарк сервиса.

Моё прежнее сравнение «вдвое точнее» смешивало эту выборку с другой, состоящей из старых ID, на которой проверялся мой оценщик. Я отозвал этот вывод. Для сравнения обоим нужны одни и те же независимо проверенные аккаунты и согласованное правило подсчёта ошибки.

Платный тариф API я не оплачивал и не тестировал. По результатам бесплатного чата нельзя судить, что возвращает этот тариф. Я также не проверил, означает ли поле `Appeared` первое наблюдение аккаунта сборщиком. Это было моей интерпретацией, а не установленным поведением сервера.

<a id="the-tgdb-conclusion-i-had-to-retract"></a>

## Вывод о TgDB, который пришлось отозвать

Из всех ошибок в этом тексте этой было проще всего избежать.

Я нашёл `tgdb_search_bot` в декомпилированном `ChatUtils.java` и объявил, что запросы `regdate` из exteraGram идут в TgDB. В ответ на реальный запрос TgDB потребовал покупку, и история показалась законченной: значок спонсора, запрос к боту, платная база.

Чтение настоящей цепочки вызовов её опровергло.

```text
RegDateController.fetchRegistrationDate
  -> ChatUtils.sendBotRequest
     -> ExteraConfig.getApiBotInfo
        -> setting: extera_api_bot
        -> default: exteraAuthBot
```

Имя TgDB относится к другому вспомогательному методу:

```text
ChatUtils.getBotInfo
  -> setting: search_bot
  -> default: tgdb_search_bot
```

Настройку API-бота можно переопределить удалённо. Изученное значение по умолчанию и цепочка вызовов показывают, что делает этот код, но не раскрывают все конфигурации, развёрнутые на стороне сервера. И уж точно не устанавливают, что за датами регистрации стоит TgDB.

Отдельный HTTP API пробел не закрыл. Методы профиля возвращали сведения о значках. Проверенный маршрут `regdate` отвечал иначе, чем несуществующие пути, и возвращал ошибки авторизации. Код `401` говорит, что авторизованный результат я не получил. Он не раскрывает базу точных дат за этим методом. Ответ `500` тоже не доказывает ни ожидаемый набор параметров, ни качество хранящихся данных.

Требование покупки у TgDB в записанном взаимодействии было настоящим. Рекламируемый охват пользователей и чатов не отвечал на мой вопрос. Сервис может хранить обширную историю участия в чатах и при этом не знать, когда аккаунт зарегистрировали. Даже надёжная временная метка первого наблюдения обычно задаёт лишь верхнюю границу даты регистрации, а не равенство с ней.

На основании этого исследования я бы доступ не покупал. Прежде чем рекомендовать оплату, я хотел бы увидеть примеры ответов для независимо известных дат, определение каждого возвращаемого поля и основания ожидать, что эти данные улучшат офлайн-оценщик. Для платного доступа к TgDB ничего из этого у меня нет.

## Что находится внутри main.py

Этот раздел описывает исходный снимок 55f968d. Его количества и смешанные holdout-оценки оставлены для истории; текущая версия описана выше.

Код скрипта я оставил простым. В нём таблица дат, таблица неопределённости, функция интерполяции с двоичным поиском и вывод в командную строку. Опубликованный файл представляет собой уже существовавший оценщик, переименованный в `main.py`, без переобучения или необъявленной смены алгоритма.

При проверке перед публикацией я заново получил результат локального генератора, не перезаписывая скрипт, и сравнил их побайтово. Они совпали.

Эти метрики пересчитаны для публикации. Они описывают полное представление модели, которое строит локальный генератор, а не новую независимую проверку на совокупности аккаунтов. Исполняемый скрипт сжимает результат подгонки: сохраняет точку, если оценённая дата сдвинулась больше чем на день относительно последней сохранённой точки, а также сохраняет концы диапазона. Затем линейно интерполирует между оставшимися точками. Поэтому опубликованный скрипт не эквивалентен вычислению всех исходных ступеней PAVA, и в таблице нет отдельной измеренной оценки ошибки именно этого сжатия.

Входная коллекция объединяет открытые данные, декодированные опорные точки из клиентов, наблюдения регистрации, месячные метки, представленные точечными временными значениями, и исторические метки из авторизаций. Сейчас, прежде чем назвать такую коллекцию датасетом дат регистрации, я потребовал бы более подробной проверки происхождения. Я сохранил эту версию, чтобы опубликованный скрипт соответствовал описанному исследованию, а не подменял его другим экспериментом без предупреждения.

Калибровочные данные жёстко встроены в код. Программа работает офлайн именно потому, что эти числа уже внутри. Арифметической формулы, которая извлекала бы дату из Telegram ID без таблицы, я не нашёл.

Частная рабочая директория с обучающими данными не опубликована. В ней есть материалы сбора, относящиеся к конкретным аккаунтам, и выкладывать их как есть было бы неправильно. Поэтому репозиторий делает воспроизводимым получение оценок, но не даёт полностью воспроизводимого обучения на сырых данных. Здесь описаны источники и алгоритм, чтобы это ограничение было видно, а не пряталось за словом «исследование».

<a id="what-would-change-the-result"></a>

## Что могло бы изменить результат

Следующим полезным вкладом стало бы новое наблюдение с известным происхождением. В строке нужно указать, какое событие измерялось, как был определён аккаунт, какой часовой пояс использован и что представляет собой временная метка: точное время, округление до дня, округление до месяца или только границу.

Регистрация, записанная в момент события, была бы надёжнее самого старого сохранившегося входа. Дата служебного сообщения с проверенной привязкой к пользователю была бы надёжнее скопированного ответа сервиса оценки возраста. Календарный месяц должен оставаться интервалом, а не превращаться без предупреждения в своё пятнадцатое число.

При оценке нужно разделять источники, а не только случайным образом делить строки. Если два репозитория скопировали одну кривую, помещение одной копии в обучение, а другой в тест измеряет согласие между копиями. Полезная отложенная выборка содержала бы независимые события, которых нет ни в одном источнике, использованном для подгонки модели. Поздние периоды нужно проверять отдельно, чтобы стареющая калибровка не казалась актуальной только потому, что старые точки всё ещё хорошо ложатся на кривую.

Для коммерческого сервиса я начал бы с той же независимой отложенной выборки и сравнивал сопоставимые ответы. Предсказание месяца требует метрики, учитывающей месячную точность. Заявление о точной дате требует проверки точной даты. Название тарифного плана в измерение не входит.

Доступный результат сейчас: скрипт выше, у которого на нынешних смешанных данных ошибки измеряются неделями и месяцами. Цель определять точный день осталась недостигнутой. Другой источник или более удачный эксперимент могут изменить эту оценку; дополнительный разряд в напечатанной временной метке не изменит.

## Источники и примечания к публикации
